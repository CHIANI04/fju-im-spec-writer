## 第一章 系統描述

### 一、需求分析與市場探索(114學年度新增,取代舊版「發展背景與動機」)

這是最容易被扣分的段落,因為AI生成容易讓各小節「各寫各的」、彼此不呼應。**撰寫時務必讓下列五小節形成一條邏輯線:問題→誰受影響→現況與痛點→競品比較→我們的定位。**

- **問題陳述**:必須包含四個要素,缺一不可:
  1. 明確定義試圖解決的「問題」是什麼
  2. 這個問題對「誰」造成了困擾
  3. 這個問題目前是如何被解決的(現況)
  4. 現有解決方案有什麼「痛點」
- **利害關係人分析**:列出所有與系統相關的「人」,不只是直接使用者(如學生、店長),也要考慮出資者、系統維護者、部門主管等。**每個利害關係人對系統的「期望」要分別說明**,不能只是列名單。
- **需求蒐集方法**:說明「如何得知」這些需求,要具體(例如:訪談了5位潛在使用者、發放80份線上問卷、觀察3次現行作業流程、參考特定法規或文獻),不能只是空泛帶過。
- **競爭者分析**:在市場上(含App Store、網路服務)找2-3個功能最相近的競爭對手或替代方案,分析各自優缺點。**不能省略這節**,這是常見扣分點。
- **市場定位/利基**:綜合以上分析,說明系統與競爭者「有何不同」、「目標客群」是誰、闡述「價值主張」。**不能缺目標客群或價值主張。**

### 二、系統發展目的

- 根據「需求分析與市場探索」描述系統的功能性需求,針對問題陳述提到的每個問題,簡單說明如何解決
- **內容必須與問題陳述一致**——問題陳述提到的問題,這裡都要有對應解方;這裡不能突然冒出新問題
- 可簡單描述非功能性需求(如效能、安全性、可用性要求)
- 附上「問題與解決方案對應表」(整理發展目的中提到的問題與解決方案,兩欄式表格)

### 三、系統範圍

- 根據使用者情境盤點任務,針對任務盤點功能性需求
- 需要涵蓋「系統發展目的」中提到的每一項解決方案,並更進一步描述功能性需求(目的是讓讀者在看第二章之前,先對系統功能有概略了解)
- **只包含這次將開發的需求**,不在此次開發範圍內的需求應列在「系統限制」,不要混在系統範圍裡
- **不要**把系統範圍寫得跟系統發展目的一樣(範圍要更具體、更完整地列出功能性需求)
- **不要**把非功能性需求放進系統範圍(系統範圍只列功能性需求)

### 四、背景知識

- 詳細描述與系統相關的背景知識,包括在發展背景中提到的現有系統、其他相關系統或競品
- 對於系統相關的新概念、新技術,要重點描述(不需要介紹已是常識的內容,如internet、電子商務、Java等)
- **背景知識的內容必須與發展背景/需求分析章節一致**——不要分析了A競品,背景知識卻介紹B競品
- 對競品的描述不能過於簡略,需要具體到功能、介面、技術特色(可搭配截圖並標號說明,如「圖一:誠品首頁」)

### 五、系統限制

- 描述**未包含在系統範圍內**的使用者需求,以及未包含的原因
- 只列「是使用者需求但這次沒做」的限制,**不要列不是使用者需求的限制**
- 對每項限制,說明這個需求對使用者的重要性,以及為何這次沒做(技術限制、時間限制、需要外部合作方配合等)
- **常見錯誤**:把系統最重要的利基(賣點)寫成系統限制;沒有依照前面分析出的問題去思考限制;前面提出的問題/解決方案,後面卻沒有對應到系統範圍或系統限制其中一項

## 第二章 軟體需求規格

### 一、功能需求

#### 使用者角色說明

- 用表格列出角色與說明(角色、說明兩欄)
- 角色要與後面user story中出現的角色**完全一致**,不能後面又冒出新角色沒說明過

#### 使用者故事對應

- 用表格列出 Epic、User Story、優先順序三欄
- **優先順序對應開發的Sprint順序**(1: Sprint 1、2: Sprint 2、3: Sprint 3)
- Epic的思考角度要以「使用者」而非「開發者」出發——同一使用者相關的user story不應該散落在不同Epic裡,除非有清楚標明對應使用者
- **Epic不能過度分割**:一個Epic下如果只有1-2個User Story,應該與其他Epic合併
- 優先順序要與後面章節(資源需求、市場測試等)呼應,不能自相矛盾

#### 使用者故事卡

每張故事卡包含:名稱、類別(Epic或User Story)、角色(As)、需求(I want)、價值(So that)、接受條件、優先順序(User Story才需要)。

**命名規則**:
- Epic、User Story的名稱一律用「動詞」開頭(例如:「訂購」、「依類別尋找產品」),不要用名詞

**角色/需求/價值撰寫規則**:
- 角色必須清楚(不能含糊)
- 需求要清楚描述使用者想要做什麼、如何解決問題或提供什麼價值
- 價值要清楚描述這個需求「解決了使用者的什麼問題」或「提供了什麼價值」——**價值不能只是需求換句話說**(常見錯誤:需求「我想要可以看到註冊的資料」,價值「因此可以看到註冊者的資訊」→這其實同一件事,沒有講出真正的價值,要問「管理者需要這個功能嗎?為什麼?」)
- 需求跟價值不能寫反(把需求當價值寫、把價值當需求寫)

**接受條件撰寫規則(這是最容易出錯的地方,務必嚴格遵守):**

- **Epic層級**:採列點式,說明所包含的User Story之間的關係(彼此獨立/不同情境,還是彼此依賴/有先後順序)。若關係複雜可搭配活動圖(Activity Diagram)。
- **User Story層級**:採Given/When/Then情境式:
  - `Given`(前提):進入這個user story前的條件,或者是**前一個(或前幾個)已完成的user story**——Given裡不可以出現「這個user story自己的步驟」
  - `When`(動作):使用者採取的動作,**必須詳述使用者輸入的資料**(例如不能只寫「消費者輸入註冊資料」,要寫「輸入姓名、住址、電話、帳號、密碼」)
  - `Then`(結果):驗證這個user story是否完成的結果,通常是使用者看到的輸出資料——**Then裡通常不應該描述後續其他user story的步驟**,因為那樣代表要驗證下一個user story也做完了
  - 有多個情境時用 `Scenario 1`、`Scenario 2`⋯⋯分開列出
  - 一個步驟內有多個動作可用`And`連接,**不會有Or**(有Or的話要拆成不同Scenario)
- 接受條件的重點在於**輸入輸出資料**的確認,**不需要**描述使用者介面操作細節(例如按了哪個顏色的按鈕)——那些屬於第三章介面設計的內容

**常見扣分點總表(User Story部分)**:
| 錯誤類型 | 說明 |
|---|---|
| 驗收條件寫成畫面規格 | 不應寫「點選藍色送出按鈕」,應寫功能性結果 |
| 需求不清楚 | 沒具體列出所需資料欄位 |
| Given/When/Then寫反 | Given不該是動作、When不該是條件、Then不該是動作 |
| Given遺漏前置user story | 沒說明這個故事依賴哪個故事先完成 |
| 缺接受條件 | 或寫得太粗略 |
| Given提到自己的步驟 | Given只能是「前置」條件,不能是本story內的步驟 |
| Then涉及其他user story | Then應只驗證自己是否完成,不驗證後續故事 |

## 第三章 軟體設計規格

### 一、資料庫設計

- 開頭要**明列使用的資料庫**(如MySQL、Firestore)
- **關聯式資料庫(RDBMS)**:
  - 「關連一覽表」:列出資料表編號、資料表名稱(真實名稱)、說明(若為英文命名需附中文說明)。若系統未使用關聯式資料庫可省略此表。
  - 「關連結構」:每個資料表逐一列出欄位編號、欄位名稱、型態、長度、說明
  - **正確標示PK(Primary Key)及FK(Foreign Key)**,FK要標明對應的資料表與欄位(格式:`FK (資料表.欄位)`)
  - 欄位型態、長度要合理
  - **所有資料表要達到適當正規化**(建議至少第三正規化3NF),若沒有做到需說明原因
  - 資料表之間不應有不合理的關聯(如非必要的一對一或多對多關聯)
  - 命名規則建議統一(見style_guide.md)
- **NoSQL**:需清楚解釋資料結構——有多少種物件、每種物件的資料結構,可用JSON範例說明
- **關連一覽表、關連結構要與功能需求(User Story)中提到的資料一致**——驗收時老師會對照檢查

詳細資料庫設計規範(來自使用者提供的資料庫設計準則文字,已整合進 `reference/database_design_rules.md`)。

### 二、介面設計

- 「介面藍圖一覽表」:編號、名稱、對應使用者故事三欄,**要與所有user story完全對應,不能遺漏任何一個**
- 「介面藍圖(畫面)」:每個畫面獨立成一張,搭配畫面截圖/線框圖+文字說明
  - 說明要清楚描述畫面上每個元件對應的動作,以及點擊後會跳到哪個介面編號
  - **一個畫面一個編號**,不同畫面不可共用編號,同一畫面不可拆成兩個編號(即使很長要分段截圖,仍算同一個畫面)
  - **不要**把同一個user story的不同畫面混在一起講,也不要把同一畫面的不同狀態(如登入前/登入後首頁)混在一張裡——應該分開,並在說明中描述兩者的關係
  - 若畫面之間的關係複雜,可搭配狀態圖(State Machine Diagram)輔助說明
  - **介面編號用「介面藍圖一覽表」自己的編號,不要誤用user story編號**

### 三、資源需求(預算經費)

分兩個部分,格式都是「經費項目、經費名稱、金額、說明」四欄表格:

1. **開發階段**:開發系統所需的人力、軟體、硬體及對應經費
   - 人力:總工時 × 時薪
   - 軟體:作業系統、資料庫、開發環境、程式語言
   - 硬體:網路、伺服器、個人電腦、手機
2. **營運階段(前三年)**:營運系統所需人力、軟體、硬體及前三年經費預估
   - 營運期間資源通常跟開發期間不同(例如維運人力不必等於全部開發人力)
   - 人力:預估工時 × 時薪

**常見錯誤**:軟硬體成本都填0(只列開發者自己現有的電腦)——**應估算上線後實際需要的軟硬體成本**(如專屬伺服器,或雲端如AWS/GCE的預估費用);人力隨便估算,沒說明為何需要這麼多人力。

## 第四章 系統專題實作成果(114學年度後)

### 一、市場測試

- 測試規劃需包含:
  - 測試目的(例如:驗證核心功能是否被需要)
  - 測試對象(需符合設定的目標客群,並說明人數)
  - 測試方法:Alpha測試(內部/親友測試)、Beta測試(開放一小群真實使用者於真實環境使用)、可用性測試(請使用者於實驗室/線上會議執行特定任務)
- 測試結果

### 二、使用者回饋

- 回饋蒐集方式(如:測試後訪談、Google問卷)
- 量化數據分析
- 質化回饋彙整
- 洞見與行動:分析(綜合回饋學到了什麼)+行動(針對回饋做了什麼修改)

### 三、未來展望

- 「系統限制」是開發前的事先評估,「未來展望」則是開發後的評估——**兩者角色不同,未來展望不是重複系統限制的內容**
- 有些系統限制若因時間不足而未能達成,可寫進未來展望(給學弟妹參考的專題方向)

## 附錄

- **分工與貢獻度說明**:表格列出每位成員在各章節/功能的投入工時,老師評分會參考貢獻度百分比。**貢獻度不完全等於工時**——有些人花少時間但貢獻大,反之亦然;若懷疑虛報貢獻度,老師會要求個別驗收確認。有兩種格式變體(數字工時 vs ★/⚪符號),見 `format_pattern_guide.md`。
- 實際畢業專題(如Beaton)另外還會有「程式分工及貢獻度說明」(區分UI/DB各自負責人)與「工作項目實際工時」(實際工時 vs 預估工時對照,算出百分比),前導課程範本沒有這兩項,是否需要應與使用者確認。
- **參考資料**:條列式列出網址或文獻,逐條編號。
- 111-113學年度版本另外還有「進度報告」(依Sprint分別列出Sprint goal、Daily Scrum摘要、測試報告、Sprint Review、Sprint Retrospective、下個Sprint規劃),114學年度後進度報告已改為另外繳交,不放入文件附錄——**生成文件前務必先確認使用者的規則版本**。
- 若專題開發過程中使用生成式AI協助,依老師規範應加註「**AI工具使用揭露聲明**」。格式為**純文字段落**(不是條列或表格),簡短說明:①使用範圍(如:術語統整、故事架構優化、文字潤飾)②所有核心設計/架構/邏輯仍由團隊成員最終審核與修正。範例參見 `format_pattern_guide.md` 附錄段落。

## 全文件層級的一致性檢查重點(最高頻扣分原因)

依老師在Documentation頁面的說明,學生因為過度依賴生成式AI,最常見的整體性問題是:**「需求分析與市場探索」、「系統發展目的」、「系統範圍」、「背景知識」、「系統限制」之間互相沒有關連**。生成文件時務必確保:

1. 問題陳述提到的每個問題 → 系統發展目的都要有對應解方
2. 系統發展目的的每個解決方案 → 系統範圍都要有對應的功能性需求
3. 系統範圍的每個功能 → 第二章User Story都要有對應
4. 背景知識介紹的競品 → 要與需求分析中的競爭者分析一致
5. 系統限制只放「系統範圍之外」的需求,不要跟系統範圍/系統限制自相矛盾
6. Epic/User Story的優先順序 → 要與資源需求、市場測試規劃呼應
