# 生成後品質檢查清單

生成或修改任一章節後,依此清單自我檢查。發現問題時,標記「⚠️待確認」而非自行捏造答案。

## 全文件一致性(最重要,最常扣分)

- [ ] 問題陳述中的每個問題,在「系統發展目的」都有對應解決方案
- [ ] 系統發展目的的每個解決方案,在「系統範圍」都有對應功能性需求
- [ ] 系統範圍的每個功能,在第二章都有對應的Epic/User Story
- [ ] 背景知識介紹的競品,與「競爭者分析」一致
- [ ] 系統限制只包含「系統範圍之外」的需求,沒有跟系統範圍矛盾
- [ ] Epic/User Story優先順序,與資源需求、市場測試規劃彼此呼應
- [ ] 使用者角色說明中的角色,與User Story中出現的角色完全一致

## 第一章 需求分析與市場探索

- [ ] 問題陳述包含:問題是什麼、對誰造成困擾、現況如何解決、現有痛點
- [ ] 利害關係人分析有說明「各自的期望」,不只是列名單
- [ ] 需求蒐集方法具體(訪談人數、問卷份數、觀察次數等),不是空泛帶過
- [ ] 競爭者分析有2-3個具體競品,含優缺點
- [ ] 市場定位/利基有明確目標客群與價值主張
- [ ] 系統範圍沒有和系統發展目的重複
- [ ] 系統範圍沒有混入非功能性需求
- [ ] 系統限制不包含系統的核心賣點/利基

## 第二章 使用者故事

- [ ] Epic、User Story名稱都是「動詞」開頭
- [ ] 每個Epic下至少有2個以上User Story(否則應合併)
- [ ] 需求(I want)與價值(So that)不是同義重複
- [ ] Given只放前置條件/前一個user story,不含本story步驟
- [ ] When有詳述使用者輸入的具體資料欄位
- [ ] Then是驗證結果/輸出資料,不涉及後續其他user story
- [ ] 多情境已用Scenario 1/2/3清楚拆分
- [ ] 接受條件沒有描述畫面操作細節(按鈕顏色等)

## 第三章 資料庫與介面設計

- [ ] 已明列使用的資料庫(MySQL/Firestore等)
- [ ] 每個FK都標明對應資料表與欄位
- [ ] 資料表達到至少3NF,或已說明未做到的原因
- [ ] 關連結構的欄位與第二章User Story所需資料一致
- [ ] 介面藍圖一覽表涵蓋所有User Story,沒有遺漏
- [ ] 每個畫面獨立編號,沒有一畫面多編號或多畫面共用一編號
- [ ] 每個介面藍圖說明清楚元件對應動作與跳轉目標
- [ ] 資源需求的軟硬體成本不是全部填0(有估算上線後實際成本)

## 第四章 實作成果(114學年度後)

- [ ] 市場測試有明確目的、對象(人數與是否符合目標客群)、方法
- [ ] 使用者回饋包含量化與質化兩部分
- [ ] 未來展望不是重複系統限制的內容,而是開發後的新評估

## 格式檢查

- [ ] 修改紀錄表格已更新本次變更
- [ ] 圖片皆有編號與標題,文中有引用
- [ ] 表格格式符合 style_guide.md 中的範本
- [ ] 章節標題層級與目錄一致
