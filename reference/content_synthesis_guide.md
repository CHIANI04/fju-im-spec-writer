# 內容合成指南:三份來源文件的優先順序與老師隱性偏好分析

> **這份文件是目前skill內建的「預設參考來源分析」,不是永久寫死的規則。** 它是基於2026年當時可取得的三份文件(111範本、114範本、Beaton音樂祭平台範例)深度比對而成。**若未來的使用者(例如學弟妹)手上有不同的參考範例文件**(老師換了新範本、有新的歷屆優秀範例),應該用同樣的分析方法(逐章節比對完整度、萃取寫作優點、找出常見扣分點對照的隱性偏好)重新產出一份對應的分析,取代或補充這份文件——**不要假設這份文件內容永遠適用**。skill在開始生成內容前,會先詢問使用者是否要套用這份預設,或改用其他參考來源,見`SKILL.md`「階段一」的說明。
>
> 這份文件是深度比對111範本、114範本、音樂祭文件(Beaton)三份來源後整理出的**逐段落來源優先策略**,以及從內容差異中反推出的「老師沒寫在規範網頁上,但從範例文件品質差異能看出來的審核偏好」。生成任何章節前,先查這份文件對應段落該用哪個來源、該注意什麼隱性偏好。

## 逐段落來源優先策略與隱性偏好分析

### 問題陳述(114新增小節)

**來源優先順序**:114範例(格式主體)+ 音樂祭/111發展背景與動機(內容深度參考),但**排除**利害關係人、需求蒐集方法、競爭者分析、市場定位的內容(這些要分配到後面各自小節,不留在問題陳述裡)。

**三份文件的實際寫法比較**:
- **114範例**(舉手系統案例):結構是「巨觀問題敘述→更聚焦的問題細節(含具體數據如「5~15分鐘」)→條列現況的因應手段(實體舉手/白板排隊/口頭分流/巡邏攔截)→逐條列出每種手段的具體缺陷」,層層收斂,越寫越具體
- **111**(阿三哥的店,舊結構):把公司背景歷史(1993年成立⋯⋯)、轉型脈絡、需求全部混在一起講,**沒有把「背景故事」跟「問題」分開**,這正是114版為何要拆分的原因
- **音樂祭**(Beaton,舊結構但內容品質較高):從產業總體趨勢(音樂祭參與人次成長)切入,收斂到具體的「資訊孤島」現象,再拆成三個子痛點(資訊整合斷裂、現場導覽斷裂、時間管理斷裂),結尾才簡短提出解決方案名稱當轉場

**萃取出的隱性偏好**:
1. **問題陳述要「由巨觀到微觀」收斂**,不能一開始就講自己系統的功能——先講產業/情境的大背景,再逐步聚焦到具體、可驗證的痛點
2. **痛點要具體、可驗證**,最好帶數字或明確情境(如「5~15分鐘」「十萬人次」),不能只寫「使用者覺得不方便」這種空泛敘述
3. **要條列現況的因應方式,並逐條指出每種方式的具體缺陷**,不能籠統帶過「目前沒有好方法」
4. **絕對不要把公司背景歷史、系統功能敘述、目標客群混進來**——111版正是因為把這些全部混在一起,才被114版拆分規則導正,寫問題陳述時要對照後面四個小節的範圍,確保不重疊

### 利害關係人分析 / 需求蒐集方法 / 競爭者分析 / 市場定位/利基

**來源優先順序**:**只有114範例有完整內容**(111、音樂祭是舊結構,沒有這四個獨立小節),直接以114範例(舉手系統案例)為主要參考。

**114範例展現的隱性偏好**:
- **利害關係人分析**:要區分同一大類角色下的「不同情境子群」(例如學生底下再分「等待驗收的學生」「等待救援的學學生」,各自又細分出「無效等待者」「成績焦慮者」「心理壓力者」「學習中斷者」等更細的心理狀態),**不是簡單列出「學生、老師、助教」三種角色就結束**,要寫出每種角色底下不同情境的具體困擾
- **需求蒐集方法**:採「分階段」結構(第一階段:現場觀察→列出具體觀察項目與觀察重點;第二階段:訪談→列出對不同角色分別要問的具體問題清單),**要展示「怎麼問、問了什麼」的具體方法論**,不能只寫「我們做了訪談」
- **競爭者分析**:每個對手要拆成「核心邏輯(一句話定調對手的產品哲學)→在自己情境下的具體缺點(逐條列出A/B/C)」,**缺點要點出「為什麼在我們的情境下行不通」,不是泛泛批評對手**
- **市場定位/利基**:要明確寫出「首要客群」「次要客群」「潛在延伸客群」三層客群,並且針對每層客群給出具體特徵描述,最後單獨寫一段「價值主張」,分別對不同利害關係人(如上面例子分「對老師與助教」「對學生」)列出具體價值點

### 系統發展目的(第一章第二小節)

**來源優先順序**:114範例的**文字段落有實際內容**(不像其他小節那麼空),但**表格(問題與解決方案對應表)是空的**,所以文字段落部分114/111/音樂祭三份都要參考,表格部分主要參考111與音樂祭(兩者都有填滿的範例表格)。

**三份文件比較**:
- **114範例**:依角色(學生視角、老師助教視角)分段描述各自希望系統做到什麼,結尾簡短提非功能性需求(易用性、反應速度、穩定性、安全性),但問題解決方案表格完全空白
- **111**:同樣依角色(老闆視角)列出具體期望(會員資料、訂單狀態、存貨管理、資安需求),表格填滿5列,每列對應「一個問題→一個解決方案」精簡對照
- **音樂祭**:先寫「系統核心理念」一段(用一句話定調系統的核心思路),再寫「主要發展目的」用分號連接的長句列出各項具體技術手段,表格填滿6列且描述更技術化(如「利用AI自抓取活動關聯的官方IG、Spotify歌單」)

**萃取出的隱性偏好**:
1. **要依角色/視角分段描述**,不要不分角色籠統寫一段
2. 問題與解決方案對應表**每一列必須能對應回問題陳述提到的具體問題**,不能無中生有新問題(老師規範網頁本來就有這條規則,三份範例都遵守)
3. 非功能性需求(安全、效能、穩定性)適合在這一節結尾簡短帶過,不需要長篇大論
4. 音樂祭示範了「先講核心理念一句話,再展開技術手段」的寫法,能讓這節更有整體感,值得借鏡

### 系統範圍(第一章第三小節)

**來源優先順序**:114範例極度精簡(只有2個bullet),參考價值低,**優先參考111與音樂祭的完整小節**,114僅供對照格式。

**三份文件比較**:
- **111**:開頭一句話點出「哪個功能滿足哪類角色的需求」,接著用數字編號(1-5)逐項描述每個功能區塊,每項都是完整段落(不是短bullet),包含操作流程細節
- **音樂祭**:同樣數字編號(一~八),但描述更技術化、更詳細(明確講到用什麼技術達成,如「透過Supabase RLS技術嚴格劃分資料存取權限」),結尾有一段總結句把所有功能串成一個完整價值主張

**萃取出的隱性偏好**:
1. **系統範圍要用數字編號逐項描述,每項寫成完整段落**(不是條列式短句),這跟`format_pattern_guide.md`裡標注的「純文字段落」規則一致,但要注意**是用編號的多段落,不是無編號的長篇大論**
2. **每個功能項目最好要能對應回第二章的一個Epic**——這樣讀者在看第二章之前已經對系統功能有概略了解(老師規範網頁本來就有這條)
3. **技術細節可以適度提及**(音樂祭的做法),但不要寫成純技術文件,仍要以「這個功能解決了什麼、怎麼用」為主軸
4. 結尾用一段總結句把所有功能串起來,呼應開頭與整體定位,音樂祭這個收尾手法值得採用

### 背景知識(第一章第四小節)

**來源優先順序**:114範例只有競品名稱清單、無內容,**優先參考111與音樂祭**。

**三份文件比較**:
- **111**:針對每個競品(誠品、金石堂)給URL,然後大量使用「截圖+編號說明」的方式(圖一~圖二十二),純粹是「帶讀者逐頁瀏覽競品網站長怎樣」,描述停留在「這個頁面有什麼區塊」的表層
- **音樂祭**:每個背景知識項目(4.1-4.4)有清楚的三段式結構——「技術背景分析」(這個競品用什麼技術)→「技術痛點」(逐條列出具體技術缺陷,編號1.2.3)→「本系統之技術轉化」(針對這些痛點,我們的系統具體用什麼技術手段解決),**每一項背景知識都直接連結回「我們的系統怎麼技術上超越它」**

**萃取出的隱性偏好(這是最關鍵的一個發現)**:
1. **111的純截圖描述式寫法,分析深度明顯不足**——只講「這個頁面有什麼」,沒有講「這代表什麼技術限制、對我們有什麼啟發」,這樣的背景知識段落**價值有限**,容易被評為「為寫而寫」
2. **音樂祭的「技術背景→技術痛點→我方轉化」三段式結構,明顯是更成熟、更有分析深度的寫法**,應該以這個結構為主要範本,而不是照抄111的截圖流水帳
3. **背景知識不是單純的「競品介紹」,而是要論證「我們的技術選型是有依據的」**——每一項背景知識最終都要導向「所以我們的系統這樣設計」的技術決策說明
4. 背景知識介紹的競品必須跟「競爭者分析」小節提到的對手一致(老師規範網頁本來就有這條)

### 系統限制(第一章第五小節)

**來源優先順序**:114、111的內容都偏少(114只有2點、111有3點,都是簡短bullet),**優先參考音樂祭的表格化寫法**,114/111僅供文字段落格式的對照。

**三份文件比較**:
- **111**:三個bullet,每個都是「使用者希望[X],但是[受限原因]」的敘述句
- **音樂祭**:改用**表格**呈現(功能項目/解決問題/可行性與限制分析三欄),每個功能項目底下用編號列出1-2個具體限制原因(技術依賴第三方API、裝置差異、環境干擾、預算限制等),表格前有一段簡短的總論(說明限制主要源於哪些類別的因素:第三方技術依賴、極端環境、裝置差異)

**萃取出的隱性偏好**:
1. **當系統限制項目較多、且每項都需要具體技術性解釋時,用表格呈現比純文字段落更清楚**——這印證了`format_pattern_guide.md`裡「系統限制可用表格」的判斷
2. **每個限制項目要具體到「哪個技術環節」「為什麼會受限」**,不能只寫「以後再說」這種空泛帶過(111的寫法偏簡略,音樂祭的技術性拆解更符合老師期待的深度)
3. 開頭用一段總論,把限制歸納成幾個類別原因(如「第三方依賴」「環境因素」「預算限制」),幫助讀者快速掌握限制的整體樣貌,再展開表格細節——這個「先總論後細節」的手法值得採用
4. **系統限制絕對不能包含系統的核心賣點**(老師規範網頁本來就有這條,音樂祭的六項限制都是次要功能的局限,沒有動搖核心價值主張,值得參考這種拿捏分寸的方式)

## 第二章:軟體需求規格

**來源優先順序**:114範例內容大多是空的(Epic/User Story對應表全空,只有一個完整範例「1 訂購」),使用者角色說明也只有半填,**優先參考111與音樂祭的完整內容**,114僅供User Story卡片格式與Given/When/Then書寫規則的參考(這部分114的規則文字本身很完整,只是範例表格是空的)。

**⚠️ 重要:寫Epic優先順序/Sprint分配前,必須先詢問使用者要分幾個Sprint**,不能自行假設數量。詢問後依「先MVP、後加分功能」的原則分配優先順序(對應Sprint 1、2、3⋯⋯),核心必要功能放進早期Sprint,加分/進階功能放進後期Sprint。

**萃取出的隱性偏好**(綜合111、音樂祭的完整範例觀察):
1. 使用者角色說明表格中,角色的「說明」欄位要具體描述這個角色的特徵、動機、限制,不能只是職稱的重複(如「員工:目前只需要負責現在的銷售⋯⋯」這種帶有情境脈絡的寫法,比單純寫「員工:負責銷售」更好)
2. Epic的命名與拆分要以「使用者的一個完整任務」為單位,不要拆得過細(這條在`chapter_requirements.md`已有記錄,111與音樂祭範例都遵守)

## 第三章:軟體設計規格

### 資料庫設計

**來源優先順序**:**優先參考114範例**(表格格式最完整、規則最明確),音樂祭與111的資料庫設計內容作為輔助對照(檢查實際案例的正規化程度、命名一致性等)。

### 介面設計、資源需求

**來源優先順序**:**優先參考音樂祭文件**(目前內容最完整、最貼近實際專題規模),114與111的內容作為格式對照輔助。音樂祭的介面藍圖涵蓋72頁的畫面設計、資源需求涵蓋開發+營運兩階段的完整表格,是三份文件中最詳盡的參考。

## 第四章:混合版結構(使用者明確選定,已知與老師「取代」措辭有出入)

**⚠️ 重要提醒**:老師規範網站明確表示114版「市場測試/使用者回饋」**取代**舊版「實作檢討」結構,用詞是「取代」而非「並存」。使用者在充分了解此風險後,**明確選擇維持六節混合版**,這是使用者的主動決定,不是skill自行判斷。**正式繳交前務必再向老師或助教確認一次這個決定是否可行。**

依使用者指示,第四章採以下六節混合結構(順序如下):

- 一、發展中遭遇到問題、困難與解決方法(參考音樂祭文件寫法:標籤+段落結構,「困難」「解決方法」各自成段)
