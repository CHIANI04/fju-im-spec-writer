# 資料庫設計規範

來源: 使用者提供之資料庫設計準則(補充老師規範中「資料庫設計」章節的細節)

設計資料庫時,必須遵循一套系統化的規範、格式與規則,以確保資料的完整性、減少冗餘並提升系統效能。

## 1. 基礎原則與規則

- **資料最低原則(Minimal Data Rule)**:「所有需要的資料都在裡面,所有在裡面的資料都是需要的」
- **實體完整性(Entity Integrity)**:主鍵(PK)必須唯一且不可為空值,確保每一列資料有明確識別身分
- **參照完整性(Referential Integrity)**:外來鍵(FK)的值必須在其參考的母表主鍵中存在,或為空值(若業務規則允許)
- **原子性(Atomicity)**:所有屬性欄位應為不可再分割的最小單元,每個行列交集只能包含單一值,不可有重複群組

## 2. 命名規範(Naming Conventions)

- **實體(Entities)**:簡短、有意義、業務熟悉的「名詞」,通常大寫表示(如`CUSTOMER`、`INVOICE`)
- **屬性(Attributes)**:具描述性,建議加上所屬實體名稱縮寫作前綴(如`CUS_LNAME`),主鍵可用`_ID`、`_NUM`或`_CODE`作後綴
- **關係(Relationships)**:使用主動或被動的「動詞」清晰表達實體間關聯本質(如`CUSTOMER generates INVOICE`)

## 3. 資料格式與定義

- 欄位一致性:同一欄位中的所有值必須符合相同的資料型態與格式
- 選擇正確的資料型態:數值(Numeric)、字元(Character)、日期(Date)——若資料由數字組成但不需數學運算(如電話號碼、郵遞區號),建議存為字元型態
- 定義域限制(Domain Constraint):為每個屬性明確定義容許的值範圍或集合(如GPA介於0.00到4.00之間)

## 4. 正規化規範(Normalization)

商業資料庫通常至少需達到第三正規形式(3NF):

- **1NF**:資料呈表格格式,無重複群組,已定義主鍵
- **2NF**:符合1NF,且消除部分相依(非主鍵屬性須依賴「整個」複合主鍵,而非其中一部分)
- **3NF**:符合2NF,且消除遞移相依(非主鍵屬性不可依賴另一個非主鍵屬性)

## 5. 商業規則(Business Rules)

- 規則須簡短、精確且無歧義
- 規則用於定義實體、屬性、關係的連結性(Connectivity,如1:M)與基數(Cardinality,如(1,N))

## 6. 設計與檢查清單

完成初步設計後,對照以下項目驗證:

- 每個實體是否代表單一主體?
- 是否有非必要的資料備援?
- 衍生屬性(Derived Attributes)是否已清楚標示並註明來源?
- ER模型是否已針對預期的資料操作(增、刪、改、查)進行驗證?

## 與老師範本格式的對應

老師範本的關連結構表格式為:編號 | 名稱 | 型態 | 說明,其中「說明」欄需標明PK/FK/AI/NN等屬性:

```
| 編號 | 名稱 | 型態 | 說明 |
| --- | --- | --- | --- |
| 1 | Id | BIGINT(11) | 編號 PK AI NN |
| 2 | CustomerId | BIGINT(11) | 顧客編號 FK (Customer.Id) NN |
```

註解: PK=Primary Key、FK=Foreign Key、AI=Auto Increment、NN=Not Null

生成資料庫設計章節時,應同時套用上述學術規範(正規化、命名一致性)與老師範本的表格格式。
