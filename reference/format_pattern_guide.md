# 段落呈現格式對照表(文字段落 vs 表格 vs 條列)

老師不喜歡「為了用表格而用表格」或「為了條列而條列」,只在資料真的適合結構化呈現時才用。以下依三份參考文件(111範本、114範本、Beaton音樂祭平台實際專題文件)歸納出**每個段落實際使用的呈現方式**,生成內容時比照辦理,不要自己決定要不要用表格。

## 第一章

| 段落 | 呈現方式 | 依據 |
|---|---|---|
| 問題陳述 | **純文字段落**,多段連續敘述 | 111/114/Beaton三份文件一致 |
| 利害關係人分析 | **純文字段落**,依角色分段敘述 | 三份文件一致 |
| 需求蒐集方法 | **純文字段落**,分階段敘述(如「第一階段」「第二階段」以粗體標示,但內文仍是段落) | 114範本 |
| 競爭者分析 | **純文字段落**,每個對手一段,可用粗體標出對手名稱與核心邏輯 | 114範本、Beaton |
| 市場定位/利基 | **純文字段落** | 114範本 |
| 系統發展目的 | **純文字段落** | 三份文件一致 |
| 問題與解決方案對應表 | **表格**(問題／解決方案兩欄) | 111/114範本明確使用表格;Beaton在此處以「可行性分析表」取代(見下) |
| 系統範圍 | **純文字段落**,可用數字編號(1. 2. 3.)分點但仍是完整敘述句,不是關鍵字條列 | 三份文件一致 |
| 背景知識 | **純文字段落**為主,每個競品/技術一個子標題,段落中可插入條列式的「技術痛點」清單(2-3點) | Beaton示範:每個背景知識子項先一段技術背景敘述,痛點才用條列 |
| 系統限制 | **純文字段落**(111/114範本)或**表格**(Beaton:功能項目／解決問題／可行性與限制分析三欄,適合功能項目多、需要逐一列可行性分析時) | 兩種皆可,依內容量選擇——若限制項目少(3-5項)用文字段落,若像Beaton一樣要逐一分析多個功能模組的可行性,用表格更清楚 |

## 第二章

| 段落 | 呈現方式 |
|---|---|
| 使用者角色說明 | **表格**(角色／說明) |
| 使用者故事對應 | **表格**(Epic／User Story／優先順序) |
| 使用者故事卡 | **表格**(名稱/類別/角色需求價值/接受條件/優先順序),卡片內的Epic接受條件用條列,User Story接受條件用Given/When/Then(段落式或條列皆可,依情境數量) |

## 第三章

| 段落 | 呈現方式 |
|---|---|
| 資料庫設計(關連一覽表、關連結構) | **表格** |
| 介面設計(介面藍圖一覽表、介面藍圖) | **表格**(一覽表)+**圖片+文字說明**(逐個畫面) |
| 資源需求 | **表格**(經費項目/經費名稱/金額/說明) |

## 第四章

依「111-113學年度版(系統專題實作檢討)」與「114學年度版(系統專題實作成果)」有不同小節,但呈現方式規律一致:

| 段落 | 呈現方式 |
|---|---|
| 發展中遭遇到問題、困難與解決方法(111-113版) | **標籤+段落**結構:「困難」「解決方法」各自成段落敘述,不是表格,但可用粗體標籤(如Beaton範例) |
| 系統優缺點SWOT評估(111-113版) | **純文字段落**,優勢/劣勢/機會/威脅各自標題下,逐點編號但每點是完整段落敘述,不是關鍵字條列 |
| 發展心得(111-113版) | **純文字段落** |
| 市場測試(114版) | **純文字段落**,含具體數字(人數、班級數)直接寫在敘述句中,不特別做成表格 |
| 使用者回饋(114版) | **純文字段落**,量化數據可用「4位(26.7%)認為相當同意」這種寫法直接嵌入段落,不做圖表;質化回饋可條列分類整理(如Beaton的「1.機制公平...:3人」格式) |
| 未來展望 | **純文字段落**,可依方向編號(一、二、三...)分段但每段仍是完整敘述 |

## 附錄

| 段落 | 呈現方式 |
|---|---|
| 分工與貢獻度說明 | **表格**,有兩種變體可選:①111/114官方範本的數字工時格式(每人每項目填工時數字,加總算百分比)②Beaton實際採用的★(主要負責)/⚪(參與)符號格式,更簡潔。**兩種都是老師認可的格式,可與使用者確認要用哪一種** |
| 工作項目實際工時 | **表格**(工作項目/實際工時/預估工時/百分比)——114學年度後,此表已改為與進度報告一起「另外繳交」,不一定要放入正式文件附錄,需與使用者確認 |
| 參考資料 | **條列**(編號列出網址/文獻) |
| AI工具使用揭露聲明 | **純文字段落**,簡短一段說明使用範圍與人工審核情形,不是條列也不是表格(見Beaton範例) |

## 生成規則總結

1. **先查這份表格**,確認該段落該用哪種格式,不要自行決定
2. 敘述性、需要邏輯連貫的內容(問題陳述、系統發展目的、SWOT、心得等)→ **一律用文字段落**,不要條列化,即使內容可以拆成幾點,也要寫成完整句子組成的段落
3. 結構化、多筆同類資料需要對照查閱的內容(角色說明、User Story、資料庫、介面、經費)→ **一律用表格**
4. 少數兩者皆可的段落(系統限制、分工貢獻度)→ 依內容量或与使用者確認採用哪一種
5. 條列式只在「同一段落內列出3項以內的短要點」時使用(如技術痛點、Epic接受條件的子項目關係),不要把整段論述拆成條列清單
