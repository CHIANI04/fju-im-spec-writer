# 段落呈現格式對照表(文字段落 vs 表格 vs 條列)

老師不喜歡「為了用表格而用表格」或「為了條列而條列」,只在資料真的適合結構化呈現時才用。以下依三份參考文件(111範本、114範本、Beaton音樂祭平台實際專題文件)歸納出**每個段落實際使用的呈現方式**,生成內容時比照辦理,不要自己決定要不要用表格。

## 第一章

| 段落 | 呈現方式 | 依據 |
|---|---|---|
| 問題陳述 | **純文字段落**,多段連續敘述 | 111/114/Beaton三份文件一致 |
| 利害關係人分析 | **純文字段落**,依角色分段敘述 | 三份文件一致 |
| 需求蒐集方法 | **純文字段落**,分階段敘述(如「第一階段」「第二階段」以粗體標示,但內文仍是段落) | 114範本 |
| 競爭者分析 | **純文字段落**,每個對手一段,可用粗體標出對手名稱與核心邏輯 | 114範本、Beaton |
| 市場定位/利基 | **純文字段落**+**價值主張圖**(圖片) | 114範本、最新確認章節參考 |
| 商業模式 | **圖**(商業模式九宮格/Business Model Canvas)+簡短文字段落逐項說明;若不適用,**純文字段落**說明原因 | 最新確認章節參考(新增小節,無既有範例可循,依老師規範的九宮格框架產出) |
| 系統發展目的(功能性/非功能性) | **純文字段落** | 三份文件一致 |
| 問題與解決方案對應表 | **表格**(問題／解決方案兩欄) | 111/114範本明確使用表格;Beaton在此處以「可行性分析表」取代(見下) |
| 系統範圍 | **純文字段落**,可用數字編號(1. 2. 3.)分點但仍是完整敘述句,不是關鍵字條列 | 三份文件一致 |
| 系統限制 | **純文字段落**(111/114範本)或**表格**(Beaton:功能項目／解決問題／可行性與限制分析三欄,適合功能項目多、需要逐一列可行性分析時) | 兩種皆可,依內容量選擇——若限制項目少(3-5項)用文字段落,若像Beaton一樣要逐一分析多個功能模組的可行性,用表格更清楚 |
| 背景知識(第一章第六節,使用者團隊決定保留) | **純文字段落**為主,每個競品/技術一個子標題,段落中可插入條列式的「技術痛點」清單(2-3點) | Beaton示範:每個背景知識子項先一段技術背景敘述,痛點才用條列 |

## 第二章

| 段落 | 呈現方式 |
|---|---|
| 使用者角色說明 | **表格**(角色／說明) |
| 使用者故事對應 | **表格**(Epic／User Story／優先順序) |
| 使用者故事卡 | **表格**(名稱/類別/角色需求價值/接受條件/優先順序),卡片內的Epic接受條件用條列,User Story接受條件用Given/When/Then(段落式或條列皆可,依情境數量) |

## 第三章

| 段落 | 呈現方式 |
|---|---|
| 資料設計(關連一覽表、關連結構;本專題為PostgreSQL/Supabase,屬RDBMS路徑) | **表格** |
| 介面設計(介面藍圖一覽表、介面藍圖) | **表格**(一覽表)+**圖片+文字說明**(逐個畫面) |
| 系統架構圖(最新確認章節參考新增) | **圖**(System Architecture Diagram) |
| 資源需求(預算經費) | **表格**(經費項目/經費名稱/金額/說明) |

## 第四章(依最新確認章節參考的官方三節結構)

| 段落 | 呈現方式 |
|---|---|
| 概念驗證(測試規劃:測試目的/測試對象/測試方法) | **條列**(三個子項各一條,內容可為完整句子);測試結果可接續寫成**純文字段落** |
| 驗證結果(回饋蒐集方式/量化數據分析/質化回饋彙整/洞見與行動) | **純文字段落**,量化數據可用「4位(26.7%)認為相當同意」這種寫法直接嵌入段落,不做圖表;質化回饋可條列分類整理(如Beaton的「1.機制公平...:3人」格式) |
| 未來展望 | **純文字段落**,可依方向編號(一、二、三...)分段但每段仍是完整敘述 |

> **歷史對照(已不採用)**:先前考慮過的「六節混合版」(發展中遭遇問題與解決方法、SWOT評估、發展心得)格式規則——問題與解決方法用「標籤+段落」、SWOT用純文字段落逐點敘述、發展心得用純文字段落——保留於此供參考,但目前第四章一律採上方三節結構,不使用這三節。

## 附錄(依最新確認章節參考的官方四項結構)

| 段落 | 呈現方式 |
|---|---|
| 一、系統文件分工及貢獻度說明 | **表格**(橫軸:組長+各組員;縱軸:文件章節/小節;內容:**百分比**,不是工時數字) |
| 二、系統分工及貢獻度說明 | **表格**(橫軸:組長+各組員;縱軸:**系統功能/User Story分類**,例如「消費者—首頁」「管理者—進貨」,不是技術角色分類;內容:**百分比**) |
| 三、AI揭露 | **圖片(10種指定Canva徽章選一張)+簡短文字說明**,不是純文字段落——務必附上徽章圖片,不能只用文字描述 |
| 四、參考資料 | **條列**(編號列出網址/文獻) |

> **選用、非官方必填**:「程式分工及貢獻度說明」(Beaton示範的UI/DB角色分工,★/⚪符號格式)、「工作項目實際工時」(工作項目/實際工時/預估工時/百分比表格)——官方結構沒有這兩項,除非使用者主動要求額外補充,否則不納入正式附錄。

## 生成規則總結

1. **先查這份表格**,確認該段落該用哪種格式,不要自行決定
2. 敘述性、需要邏輯連貫的內容(問題陳述、系統發展目的、SWOT、心得等)→ **一律用文字段落**,不要條列化,即使內容可以拆成幾點,也要寫成完整句子組成的段落
3. 結構化、多筆同類資料需要對照查閱的內容(角色說明、User Story、資料庫、介面、經費)→ **一律用表格**
4. 少數兩者皆可的段落(系統限制)→ 依內容量或与使用者確認採用哪一種
5. 條列式只在「同一段落內列出3項以內的短要點」時使用(如技術痛點、Epic接受條件的子項目關係),不要把整段論述拆成條列清單
6. 需要圖片的段落(商業模式九宮格、價值主張圖、系統架構圖、AI揭露徽章)→ **一律搭配圖片**,不能只用文字描述代替
